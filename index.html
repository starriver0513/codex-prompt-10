PROMPT 01

安全性と機能性をMAXにする
.envファイル設定プロンプト

APIキーを安全に保存する場所を作ります。ここが10本の土台です。

API（外部のサービスとAIを連携する仕組み）を繋ぐと、Codexができることが一気に増えます。例えばYouTubeのAPIを繋ぐと、再生数やコメントを直接取ってこれるようになります。画像を作るのもリサーチも、裏では全部このAPIを使います。

その連携に必要なのがAPIキー（サービスごとに発行される、自分専用の暗証番号）です。APIキーはパスワードと同じで、チャットに貼るとログに残ります。なので .env（エンブ）という隠しファイルに置いて、AIにはそこを読ませて、チャットには絶対に貼らない。このプロンプトは、その保存場所を作って、「値は表示しない」「勝手に送らない」というルールまでAIに書かせます。

これを入力すると、使うサービスを聞かれるので答えます（本編ではYouTubeとOpenAIにしました）。.envができて、キーを貼るところで止まるので自分で貼ります。貼ったら、AIが「埋まっているか・文字数」だけ確認して、読み取りのテストをしてくれます。

# APIキーの置き場所（.envファイル）を作ってください

あなたは、私のパソコンのこのフォルダで作業するAIエージェントです。
外部サービスのAPIキーを安全に置く「.envファイル」の仕組みを作ってください。
これ以降、私は「.envにキーが入っている前提」で色々な仕事をあなたに頼みます。

## 最優先の安全ルール
1. APIキーやトークンの「値」を、チャット・ログ・ファイル名・報告文に絶対に出さない。確認が必要な時は「設定済み／未設定」と「文字数」だけを答える
2. .env を cat や Read で丸ごと読まない（読むと値が画面と会話ログに残る）。確認は「変数名と文字数だけを出すコマンド」で行う
3. もし私がチャットにキーの値を貼ってしまったら、復唱も保存もせず「そのキーは公式画面で再発行して、古い方は無効にしてください」と案内する
4. 分からない仕様は推測で埋めず「未確認」と言う。URLは公式サイトで確認できたものだけ書き、確認できなければ「公式サイトで『サービス名 API key』を検索」と案内する

## 手順（質問は手順2の1回だけ。例外は手順1でフォルダの場所が悪い時だけ止まってよい。あとは止まらず進め、手順7で私が「貼りました」と言うまで待つ）
1. 今いるフォルダを表示し、.env / .env.example / .gitignore が既にあるか表で報告する。今いる場所がホーム直下・デスクトップ・書類直下や、iCloud Drive / OneDrive / Dropbox / Google Drive の同期対象の中なら、ホーム直下に `Codex用フォルダ`（動画と同じ名前）を作ることを提案し、私のOKを待つ。作ったら「Codex（またはClaude Code）でそのフォルダを開き直してから、このプロンプトをもう一度貼ってください」と案内して止まる（開いているフォルダの外では続けない）
2. 私が使う予定のサービスをまとめて聞く（例: YouTube Data API / X API / OpenAI / Google / Chatwork）
3. .env.example（変数名=のみ。値なし。変数名は各サービスの公式が使う標準名。例: OPENAI_API_KEY / YOUTUBE_API_KEY / X_BEARER_TOKEN / CHATWORK_API_TOKEN）を作り、それをコピーして .env を作る（.env が既にある場合は上書きせず、足りない変数名の行だけ追記する）。値は私が自分で貼る。あなたはキーの値を作らない・推測しない
4. .gitignore に `.env` `.env.*` `!.env.example` をこの順で追記する（既にある行は飛ばす）。このフォルダがGit管理されていなくても作る（あとでGitを使い始めた時に .env が漏れないための保険）
5. サービスごとに「公式の発行ページの名前と、キーを取る大まかな手順、料金の有無」を3行以内で案内する。従量課金のサービスは、公式画面で月の上限額を設定するよう促す。キーの発行に10〜20分かかることがあると先に伝える
6. .env を私が編集できるように開く。.env は隠しファイルで普段は見えないことを先に伝える。Mac: あなたが `open -e .env` を実行してテキストエディットで開く（実行できなければ「Finderでこのフォルダを開き Command+Shift+. を押すと .env が見える。ダブルクリックで開く」と案内する）／Windows: `notepad .env`（保存時に `.txt` が付いていないか確認してもらう）
7. 私が「貼りました」と言ったら、変数名／設定済みか未設定か／文字数 の表で確認する（値は出さない）。設定済みのキー1つで、読み取り専用の疎通確認を1回だけ行い、成功／失敗だけ報告する（例: OpenAI=モデル一覧の取得、YouTube=公開チャンネル1件の取得）
8. このフォルダのルールファイルに次のルールを追記する。CLAUDE.md（Claude Code用）と AGENTS.md（Codex用）のどちらも無ければ、両方作って同じ内容を書く:
   - 認証情報は .env ファイルから読む。コードやチャットに直接書かない
   - 外部への送信・投稿・削除・課金は、私が「はい」と言うまで実行しない
   - 新しいAPIやMCPを繋ぐ時は「読み取り → 下書き → 限定的な書き込み」の順で広げる

ディレクトリ構築プロンプト

AIが作業するフォルダの構造を一撃で作ります。

AIの出力の質は、指示出しの質と、渡す情報の質の掛け算で決まります。みんな指示出しは頑張るんですが、情報の整理ができていない。情報をごちゃごちゃのまま渡すと、AIはどこを見ればいいか分からなくて、出力が一般論になります。なのでフォルダを整理して、情報の置き場所を決めます。

## Phase 3: 既存ファイルの振り分け

Phase 1 でスキャンした全ファイルを、以下の判断フローで振り分けてください。
すでに `directory.md` が存在する場合は、この判断フローより `directory.md` を優先し、必要に応じてこのv1.1方針を追記してください。

### 振り分け判断フロー

```
ファイルを1つ取り出す
    ↓
Q1. ナレッジテンプレートの1つか?（パーソナル/プロダクト/コンテンツ）
    YES → 🌐共通ナレッジ/📌共通ナレッジ/{該当ナレッジ}/ に配置
    NO  → Q2
    ↓
Q2. 事業部横断で再利用される「抽象的な知識」か?
    YES → 🌐共通ナレッジ/📌共通ナレッジ/{該当カテゴリ}/ に配置
    NO  → Q3
    ↓
Q3. 外部ツールからの未加工データか?（Googleドキュメント/スプレッドシート/音声/動画 等）
    YES → 🌐共通ナレッジ/📌コンテンツ元本/{ツール名}/ に配置
    NO  → Q4
    ↓
Q4. AIスキルまたはスキル関連ファイルか?
    ├─ YES → Q4-A
    └─ NO  → Q5
    ↓
Q4-A. どの事業部・部署・継続タスクで使うか?
    ├─ 明確 → 📦事業部/{事業部名}/{部署または業務}/スキル/{スキル名}/ に配置または参照接続
    ├─ 事業部横断 → 📦事業部/{事業部名}/事業部管理/スキル/{スキル名}/ に配置または参照接続
    └─ 不明 → 要確認リストへ（勝手に中身を書き換えない）
    ↓
Q5. どの事業部の仕事に直結するか?
    ├─ 特定の事業部に属する → 📦事業部/{事業部名}/{部署または業務}/{適切なサブフォルダ}/
    ├─ 複数の事業部で使う → Q2 に戻る（共通ナレッジの可能性）
    └─ どこにも属さない → Q6
    ↓
Q6. 将来使う可能性はあるか?
    YES → 🗂️アーカイブ/ に退避
    NO  → そのまま放置（後で判断）
```

### 振り分けルール

- **元本は1箇所**（同じ元本を複数箇所にばら撒かない）
- 事業部で使うナレッジは、元本を動かさず `ナレッジ/コピー候補/` へコピーし、`source:` と `target_task:` を先頭に残す
- スキル本文は原則変更しない。変更してよいのは、パス、参照先、README、INDEX、frontmatter、関連タスクなどのメタ情報
- `.claude/skills/` から事業部配下へ移す場合は、まずコピーまたはミラーで動作確認し、必要なら互換用READMEやリンクを残す
- ファイル名は `YYYY-MM-DD_{種類}_{テーマ}.md` に統一
- バイナリファイル（音声/動画/画像）は `.md` のメタファイルを隣に作る
- 振り分けに迷ったら事業部側に置く（後で共通ナレッジに昇格できる）

振り分け完了後、以下を報告してください:
- 各フォルダに何ファイル入ったか一覧
- スキル配置の更新件数（.claude配下 / 事業部配下 / 要確認）
- ナレッジコピー候補の作成件数（source / target_task つき）
- 振り分けに迷ったファイルのリスト（あれば）

# 毎朝9時に「今日やること」をDiscordに届ける「おはようスキル」を作って、定期実行まで設定してください

（あなたがCodexなら: 連絡アプリの接続＝プラグイン、またはMCPサーバー設定／スキルの置き場＝ `.agents/skills/`（スキルクリエイターは同梱）／定期実行＝ChatGPTデスクトップアプリの「スケジュール」機能／スキルの呼び出し＝`$スキル名`。あなたがClaude Codeなら: コネクタ／ `.claude/skills/` ／デスクトップアプリのスケジュール機能／スキルの呼び出し＝`/スキル名`。以下はこの読み替えで進めてください）

## 目的
秘書がいなくても、日本時間の朝9時にスマホを見れば「今日何をやればいいか」が一瞬で分かる状態にする。

## ゴール（このプロンプト1回で全部やる）
A. 接続確認 → B. スキル作成 → C. 今すぐ1回テスト実行 → D. 毎朝9時の定期実行を登録 → E. 完了報告

## A. 接続確認（読み取りだけ）
1. 私が使っている連絡アプリを聞く（Googleカレンダー／Gmail／Discord／Chatwork／Slack など）
2. それぞれ、APIかMCP（コネクタ）で読めるかを実際に読んで確認する。読めないものは、接続方法（コネクタの追加手順、またはAPIキーの取り方と .env の変数名）を番号つきで案内する。繋がらない情報源は飛ばして、残りで作る（後から足せる作りにする。飛ばした理由は完了報告に書く）
3. 通知先はDiscordのWebhook（チャンネルに投稿するためのURL）一本にする。作り方を案内する（Discord → 通知したいチャンネルの設定 → 連携サービス → ウェブフック → 新しいウェブフック → URLをコピー）。URLは .env の `DISCORD_WEBHOOK_URL` に私が貼る（URL自体が投稿権限なので値を表示しない）

## B. スキル作成
スキルクリエイター（スキルを作るためのスキル）があれば使って `ohayo` というスキルを作る。無ければ `.agents/skills/ohayo/SKILL.md`（Codex）または `.claude/skills/ohayo/SKILL.md`（Claude Code）を直接作る。中身は同じ:
1. 前回の実行以降に届いたメール・チャットを読み、返信が必要なもの・期限があるものを抜き出す（実行のたびに「最終実行時刻」をファイルに保存し、次回はそれ以降だけ読む。初回は過去24時間）
2. 今日のカレンダーの予定を並べる（時刻つき）
3. 「今日やるべきこと」を優先順に5個以内で書く。優先の決め方: 今日の固定予定と締切 → 外の人を待たせている連絡 → 売上やお客さん対応に直結するもの → その他
4. 最後に一言、私を元気づける言葉を添える（大げさにしない）
5. できあがった報告をDiscordのWebhookに投稿する

守ること:
- 読み取り専用。返信・送信・削除・予定の変更は絶対にしない
- 情報が取れない項目は、それらしく埋めずに「（取得できず）」と正直に書く。予定やタスクを推測で作らない
- 報告にメールアドレス・金額は貼らない。人名は姓だけ書いてよい
- 全体で400文字以内。冒頭は「☀️ おはようございます｜M月D日(曜)」の1行
- 通知先・情報源・件数・時刻はスキル冒頭の設定欄にまとめ、本文には直書きしない（あとで変えやすくする）

## C. テスト（登録して終わりにしない）
今すぐ1回だけ手動実行して、実際にDiscordに届くところまで確認する。届かなければ原因を切り分けて直す。私が直したい所を言うので反映する。可能なら（手順Dの登録が済んだあとに戻ってきて）、スケジュールの「今すぐ実行（テスト）」からも1回走らせ、無人の設定のままでプラグイン経由の情報源（Gmail・カレンダー）が読めることと、Discordに届くことを確認する。読めなければ .env のAPIで読める情報源に切り替える

## D. 定期実行
1. 原則、AIアプリ内のスケジュール機能（このパソコンで動くもの。Codexなら ChatGPTデスクトップアプリの「スケジュール」、Claude Codeならデスクトップアプリのスケジュール）に「日本時間 毎朝9:00 に $ohayo を実行（新しいスレッドで）」を登録する。クラウドで動くタイプはこのパソコンのファイルや .env が見えないので使わない
   - 定期実行は無人で走る（許可を求めずに進む設定になる）ので、途中で許可が必要な操作があるとそこで失敗して走り切らない。登録する前に、手順Cのテスト実行で許可待ちが1回も出ないことを確認する。出るなら、必要な範囲だけ（このフォルダの読み書き＋Webhook送信のためのネット接続）を許可する設定にして再テストする。Codexは既定でネット接続が切られているので、Webhook送信のために設定ファイル（ホームの `~/.codex/config.toml`）に `[sandbox_workspace_write] network_access = true` を入れる（全権限の「Full access」にはしない）
2. その機能が使えない場合（Codex CLI・エディタ拡張・機能が見当たらない時）だけ、OSの標準機能（macOS/Linuxは cron、Windowsはタスクスケジューラ）で登録する。その場合、アプリで繋いだプラグイン／コネクタ経由の情報源は使えないことがあるので、まず .env のAPIキーで読める情報源だけで組み、実行許可を求めない設定は「読み取り系のツールとWebhookへの送信」だけに限る（全部許可にしない）。どちらを使ったか、理由と一緒に私に説明する
3. 登録内容と、次回いつ実行されるかを私に見せる
4. 実行結果（成功／失敗と1行要約）を毎回 `ログ/ohayo_YYYY-MM.log` に残す。失敗が2回続いたらDiscordに「止まっています」とだけ送る
5. 私に伝える注意: この仕組みは私のパソコンで動くので、パソコンとアプリが起動している時だけ動く。スリープや電源オフだと動かない（閉じている間の分が後から動くかはアプリによる。Codexは公式に明記が無いので「動かない」前提で考え、初週は翌朝ログで確認する）。月に1回くらい、繋いだサービスの認証が切れて再ログインが要ることがある。朝の報告が来ない日はまずログ（`ログ/ohayo_YYYY-MM.log`）を見る（Webhook自体が壊れた時は「止まっています」通知も届かないため）
